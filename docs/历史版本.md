# 历史版本（设计定稿）

> 一句话：每章每次被改写，旧稿都留一版；右栏第八页按时间线看得到、回得去。

## 1. 为什么不能只有「备份文件」

原来的 `chapters/.history/<章id>-<时间戳>.md` 只做到「没毁掉」，做不到三件事：

- 不知道哪一版是**因为什么**留下的（手改？按文风重写？恢复？）
- 不知道那一版**多少字**、用的是**哪套文风**
- 没有任何界面，等价于「有备份但没人会去找」

## 2. 存储（扁平目录，零迁移）

```
chapters/.history/
  0001-20261112014406.md      旧稿正文（纯文本，MarkdownView 可直接渲染）
  0001-20261112014406.json    这一版的元数据
```

```json
{
  "version": "20261112014406",
  "chapter": "0001",
  "title": "第一章 十点四十七分",
  "chars": 1109,
  "hash": "3f1c9a2b7d0e",
  "source": "write:replace",
  "note": "按文风重写",
  "style": "湖城夜行",
  "createdAt": "2026-11-12T01:44:06.000Z"
}
```

规则：

- **文件名沿用现有规则**（`<章id>-<stamp>.md`，stamp = 紧凑 ISO14 位），所以已有的历史文件**不用迁移**，没有 `.json` 就按 `source: "legacy"` 推算（chars 现算、hash 现算、createdAt 由 stamp 反解）。
- `source` 取值：`write:replace` / `write:append` / `restore` / `legacy`。
- **内容相同不产生新版本**（sha1 前 12 位比对最新一版）：点两次保存什么都没改，不该多一条时间线。
- 同一秒写两次：版本号追加 `-2`、`-3`。
- 历史只增不减，**不做任何自动删除**（作者的定稿：永久保留）。

## 3. 宿主接口

工具：

| 工具 | 作用 |
|---|---|
| `novel_write(..., note?)` | 覆盖/追加前自动留一版，`note` 一句话写进时间线 |
| `novel_history({ chapter })` | 列这一章的时间线（版本、时间、字数、来源、备注、文风） |
| `novel_history({ chapter, version })` | 读某一版全文 |
| `novel_restore({ chapter, version })` | 恢复到某一版；**恢复前先把当前内容也留一版**，所以恢复本身可撤销 |

HTTP（只读三个 + 写一个，写接口仍要 `x-novel-action: 1`）：

- `GET /novel-api/history?chapter=` → `{ chapter, current: { chars, hash }, versions: [...] }`
- `GET /novel-api/history-all` → `{ chapters: [{ id, title, chars, versions, lastAt }] }`
- `GET /novel-api/version?chapter=&version=` → `{ version, chars, content, meta }`
- `POST /novel-api/restore` `{ chapter, version }` → `{ ok, chapter, version, chars, snapshot }`

## 4. 界面（右栏第八页「小说版本」）

- 顶部：章节下拉（默认带当前章）+ `当前 1037 字 · 6 个版本`
- 主体：**竖时间线**，每条 = 圆点 + 时间（`今天 14:04` / `昨天 23:10` / `11-10 09:22`）+ 徽标（字数 / 来源 / 文风）+ 备注
- 每条的动作：`看这版`（展开正文）/ `对比当前`（段落级差异：绿=新增、红=删除、灰=未变）/ `恢复到这版`
- 恢复要**二次确认**（按钮变「确认恢复？」，3 秒内再点才执行），恢复后自动回到章节页
- 页底 AskBar（head `版本讨论`，上下文 = 这一章的时间线清单）

## 5. 安全

- 恢复前先快照 → 恢复也能撤销
- 写正文用「临时文件 + rename」原子替换，避免半截文件
- 时间线是只读视图，唯一写动作是 `restore`

## 5.5 谁在写历史（三种来源 + 一个看门狗）

不信模型「记得做」，只信代码路径：

| 来源 | 触发点 | 说明 |
|---|---|---|
| `write:replace` / `write:append` | `novel_write` 的 `execute` 里，写盘**之前** | 旧稿非空且内容有变才留版；**没有开关**，参数里不存在 `backup: false` |
| `restore` | `novel_restore` 恢复前 | 当前内容先留一版，所以「恢复」本身可撤销 |
| `external` | 读状态 / 读时间线时（`/novel-api/state`、`/history`、`novel_status`，节流 8 秒） | **漂移看门狗**：`chapters/.history/<id>.last.md` 记着上次见到时的正文；发现文件被工具之外的写入改过，就把「上一份已知内容」补成一版 |

看门狗存在的理由：模型完全可以不用工具、直接用 `write`/`pwsh` 改章节文件（真实发生过——某本书整本就是这样手写出来的，一个快照都没留下）。工具内部靠快照，工具外部靠这条兜底。

它保证的是「**被覆盖的那一版不会凭空消失**」，不保证「每一稿都在」。外部写入的那一刻到下一次读状态之间的中间态抓不到——这是文件系统层面能做到的上限，不是插件偷懒。
## 6. 不做（v1）

跨章全文 diff、版本命名（tag）、分支/合并、云端同步、自动过期清理。
