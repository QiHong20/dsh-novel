# 小说助手 · 设计草案（历史）

> **已定稿，本文仅作决策记录。** 现行路线图、数据契约与技术红线见 [功能规划.md](功能规划.md)。
> 本文第二节的 A–E 切面里，A（书模型）与 B（工具面）已在 v0.1 落地；C（上下文装配）与 E（风格守卫）排进 v0.2/v0.3；D-重（书稿视图）推后。

状态：方向待定（等作者拍板）。下面先列出可选的切面，每个都标了它要动 DSH 的哪一层，
以及「改动半径」——方便决定先做哪一块。

## 一、这个插件到底替作者解决什么问题

一句话：**让模型在写第 87 章的时候，还记得第 3 章埋的那个伏笔，并且不会把主角的妹妹改名。**

长篇创作的真正成本不在「生成一段文」，而在三件事：

1. **资料一致性**——人物、地点、势力、时间线、专有名词，靠聊天上下文兜不住。
2. **推进结构**——卷/章/大纲/当前进度，需要结构化存储，而不是散落在几十个会话里。
3. **文风约束**——每次续写都要重复交代语气、人称、节奏、禁忌用词。

对应地，插件的发展方向是「资料库 + 进度机 + 风格守卫」，而不是「一个写小说的 prompt」。

## 二、能力切面（按改动半径从大到小）

### A. 书库服务（宿主 · 地基）
作品 → 卷 → 章 → 场景的树形数据；人物卡、设定条目、时间线事件；全部落盘成人类可读的
Markdown + 一份 JSON 索引（作者随时能用编辑器改，插件不并购）。

- 动的是：宿主半边新增一个 `novel` 服务 + 文件存储
- 半径：大（决定后面所有东西的数据形状），但无 UI 也能先跑

### B. 工具面（宿主 · 让模型会用书库）
给模型一组工具：`novel_outline`（读/写大纲）、`novel_chapter`（读/写章节）、
`novel_cards`（人物/设定检索）、`novel_continuity`（一致性检查：新写的一段和资料库冲突在哪）。

- 动的是：`ctx.tools.register` + 参数 schema
- 半径：中；做完就能「在对话里直接写小说」，不依赖任何 UI

### C. 上下文装配（宿主 · 省钱又保真）
每次续写只装相关的那一小撮资料：当前章大纲 + 出场人物卡 + 相关伏笔 + 最近两章结尾，
而不是把整本书塞进去。这是「长篇小说能写下去」的关键工程点。

- 动的是：会话投影 / 系统提示装配 / 检索（本地 BM25 或向量都行，先 BM25 够用）
- 半径：中大；和 B 一起做效果最明显

### D. 创作面板（客户端 · 界面）
两种粒度，先做轻的：

1. **轻**：`conversation.input.dock` 一条「当前作品 · 第 N 章 · 字数/进度」，点开是淡出面板。
2. **重**：`conversation.view` 注册一个「书稿」视图 tab，左边章节目录树、右边正文编辑。

- 动的是：slot 座位 + 前端状态
- 半径：轻版一天内；重版是个正经前端工程

### E. 风格守卫（宿主 + 客户端）
一份「文风契约」（人称、时态、节奏、禁忌词、口癖），续写前注入、续写后自检（有没有 OOC、
有没有出戏的现代词），结果作为提示挂在消息下方。

- 动的是：`conversation.chat.assistant-actions` 或工具返回的卡片
- 半径：小到中，很适合作为第二个可演示的能力

## 三、建议的推进顺序

```
A 书库(最小版：作品/章/人物卡，Markdown 落盘)
  → B 工具面(4 个工具)
    → C 上下文装配(先 BM25)
      → D 轻面板(进度条)
        → E 风格守卫
          → D 重面板(书稿视图 tab)
```

每步都能独立演示，且前一步是后一步的地基。若想更快看到「插件真的在跑」，
可以把 D-轻 提前到 B 之后（它只依赖一个投影）。

## 四、待定的产品问题

1. **书库放哪**？`$DSH_HOME/novel/`（跟着 DSH 走，多设备不同步）还是用户指定目录（如 `E:\workspace\idea-workspace\novel-projects`，方便 Git 管理）？
2. **一章的粒度**？按「章节文件」保存（作者心智模型）还是「场景块」（模型更好定位）？建议：章节文件 + 场景分隔符，两者兼容。
3. **冲突怎么报**？只提醒（软）还是阻止写入（硬）？建议先软。
4. **是否需要多作品并行**？影响 UI 是「单作品」还是「书架首页」。
5. **中文标点/排版规范化**要不要做（引号、省略号、破折号、段首缩进）？这属于低成本高观感的点。

## 五、已确认的技术事实（写代码时的前提）

- 宿主插件契约：`export const name / inject / Config / apply`；`defineTool` 来自 `@deepseek-ai/dsh-tools`，`z` 来自 `@deepseek-ai/schemastery`。
- 客户端 bundle 不是 ES 模块，是 `window.__ModuleLoader__.load({ id, factory })`；`factory(require)` 里的 require 只能命中平台基座（react / react-dom / cordis / 静态 UI 库）。
- 客户端插件用 cordis 插件形式导出：`exports.name / exports.inject / exports.apply`，`inject` 里写 `['slots']`（要 i18n 再加 `'locale'`）。
- 座位注册：`ctx.slots.inject('<slot>', () => ctx.slots.register({ name, id, order }, props => h(Comp, props)))`，全部包在 `ctx.effect(fn, 'label')` 里以便卸载时回收。
- CSS 用 `document.createElement('style')` + `data-plugin` 归属标记，色值一律走 `--dsw-alias-*` 变量。
- 这台机器上真正在跑的 DSH 是 **`0.2.2-rc.1`**（打包版，代码在 `resources\app.asar` 里；`dsh --version` 可验）。`~/.dsh/profiles/node_modules` 里那套 0.1.2-rc.1 是旧 npx 缓存留下的 junction，别拿它的类型当真。
- 本项目**不写** `engines.dsh` / `dsh.compatibility.dsh` 闸门（会挡住 `link:` 安装）。
