# 这本书的写作约定（给 AI 的作业规范）

这个目录是一本小说，不是代码项目。下面是**唯一可信的格式约定**——按它写，右栏的章节/章纲/人物/设定/大纲五个页面和 `novel_*` 工具才能正确读到。

## 目录结构

```
book.json          章节清单（真相来源：章节 id、标题、文件、状态、目标字数）
outline.md         整本大纲（一句话 / 主线 / 约束）
beats.md           章纲（每章一节，写正文前先看它）
threads.md         伏笔表（人工维护的 Markdown 表格）
ledger.md          当前状态快照（钱/境界/道具/伤势/时间；不保存历史版本）
characters/        人物卡，一人一个 `名字.md`
settings/          设定，一个条目一个 `条目名.md`
chapters/0001.md   正文，一章一个文件
```

**不要新建别的目录来存稿子**，也不要复制一份到别处——`chapters/` 是唯一正文所在。

## 作者不会说工具名，你要自己翻译

作者只会用日常说法，把"想要什么结果"讲出来。你负责选工具，不要让他先学工具名，也不要反问他"要不要用 novel_write"。对照表：

| 他说 | 你要做 |
|---|---|
| 「拆一下这本书」「这本书帮我拆下书」 | **把它建成一本能接着写的书**：先 `novel_import({ source, dryRun: true })` 看清切出来多少章，再沿用切分参数调用 `novel_import({ source, limit: N, dryRun: false })` 把原文**搬**进 chapters/（不要自己抄正文）→ 需要摘要时再用 `novel_write` 补 → `novel_card` 主配角 → `novel_setting` 地点/规矩/物品 → `novel_threads` 埋设与回收 → `novel_beats` 每章场景 + `→ 爽点` / `→ 钩子`。默认保留并跳过已有章节；只有作者明确要求覆盖时才加 `replace: true`。**不要交分析报告当成果** |
| 「写第三章」/「接着写」 | `novel_context({ chapter })` 拿装配包 → 按它写 → `novel_write` → `novel_deai_pack` 全文审稿与必要修改 → `novel_deai_review` → `novel_check` |
| 「这章有问题吧」/「帮我查一下」 | `novel_check({ chapter })`，然后只讲要改的三件事 |
| 「按 XX 的风格写」 | 有文风卡就 `novel_context` 带上；没有先用 `novel_style({ clone: true, source })` 生成待校准卡 |
| 「加个人物」「这个人改成…」 | `novel_card`（一张一个文件，含 `## 关系` / `## 状态`） |
| 「记一条设定」 | `novel_setting`（一条一个文件，首行 `- 分类：…`） |
| 「埋个伏笔」「这个伏笔收了」 | `novel_threads`（不要手改 `threads.md`） |
| 「查一下现在有多少钱/什么境界/东西放哪了」「更新一下状态」 | `novel_ledger`（不要手改 `ledger.md`；它只保留当前值，旧章状态查前文或已有证据） |
| 「列个章纲」「这章要有哪几场」「改一下章纲」 | 新增或整章重写用 `novel_beats`（必须写 `### 场景 英文ID：标题` + `- 时序：` + `- 出场：` + `#### 人物 ID`）；只改已有章纲的单个字段用 `novel_stage_edit` |
| 「大纲看看」/「改大纲」 | `novel_outline` |
| 「这版不如上一版」/「回到刚才那稿」 | `novel_history` 看时间线 → `novel_restore` |
| 「这本书现在什么状态」 | `novel_status` |
| 「导入我写的 txt」 | `novel_import({ source, dryRun: true })` 探测切分 → 确认后沿用切分参数调用 `novel_import({ source, dryRun: false })` 原样搬进 chapters/（边界怪就给 `ranges`/`pattern`）→ `novel_status` 核对。默认保留并跳过已有章节；只有作者明确要求覆盖时才加 `replace: true` |

两条底线：**正文只走 `novel_write`**（用 `write` 直接写 `chapters/` 会没有历史版本）；**"拆书"默认是要建书，不是要报告**。

## 人物卡格式（最容易写错，务必照抄小节名）

```markdown
# 老周

一句话说清这个人是谁。（这一行会成为「摘要」）

- 表面：爱笑，记性好。
- 里子：账册的旧主人。
- 外貌锚点：一双总笑成弯月的眼睛，袖口常年别着一枚擦得发亮的铜算盘扣。
- 性格：重情义又精明，遇事习惯先笑三秒再把账算清；底线是自己人绝不亏待、外账绝不留糊涂字。
- 口癖：称林小满为「少东家」。
- 说话：老掌柜腔，温厚里带点幽默反问，句尾爱落「呢/啊」缓和气氛，从不板着脸训人。「少东家，这账可不是这么算的——您先喝口茶，听老头子慢慢掰扯？」

## 关系
- 林小满：看着长大的孩子。
- 林小满 @0004：少东家开始不信他了。

## 状态
- @0003 去世（雾港码头失足落水）
- @0004 现身（其实没死，躲在旧货铺后屋）
```

规则：

- `## 关系` 下只能是 `- 名字：说明`；名字后可跟 `@0004` 表示「第 4 章起才成立」。**只记起点，不记终点**。
- `## 状态` 下只能是 `- @0003 状态说明`；一条状态持续到下一条为止。不含死亡词的状态（现身/复活/回到雾港）＝又活着了。
- 死亡词：去世 / 死亡 / 死 / 殁 / 阵亡 / 身亡 / 牺牲 / 遇难 / 丧命 / 不在了。写「没死、假死、装死」**不算**死。
- 这两节之外，`名字 @0004` 这种写法没有任何效果，别在别处用。
- 只写这本书里**真的会用到的**人物，路人甲乙不要建卡。

## 设定格式

```markdown
- 分类：规矩

雾港的规矩：收伞只能门外、雾天不点灯、簿子不外借。
```

首行必须是 `- 分类：...`（地点 / 规矩 / 物品 / 术语 / 组织 / 历史 / 其他），第一句正文会成为摘要。**一个可被点名的东西一条**：写第三章需要的是「账册」这一条，不是整本世界观。

## 章纲格式

```markdown
## 0003 第三章 旧客

- 事件：主线-1
- 本章目标：查清后屋来客身份，保住账册。

### 场景 s0003-backroom：旧货铺后屋

- 时序：10
- 故事时间：次日深夜
- 地点：旧货铺后屋
- 视角：lin-xiaoman
- 出场：lin-xiaoman
- 冲突：想找老周问账册，却撞见后屋有人住过的痕迹。
- 叙述方式：限知

#### 人物 lin-xiaoman
- 已知：老周昨晚失踪。
- 未知：后屋住过的人是谁。
- 目标：找到账册线索。

- → 钩子
```

二级标题以 **4 位章 id 开头**，每场必须用 `### 场景 英文ID：标题`（ID 仅限英文、数字、连字符）配 `- 时序：`、`- 出场：` 与 `#### 人物 英文ID`，否则右栏章纲页无法渲染结构化卡片且 `novel_beats` 会拒绝写入。局部改字段优先用 `novel_stage_edit`，**不要写旧版 `- 场景：谁 → 在哪` 逐行格式**。章纲里不写对白和描写。

**节奏标记（写在场景末尾，插件会统计，不另建表）**

```markdown
## 0007 第七章 开户

- 场景：江野 → 银行柜台 → 想开户存第一笔钱 → 撞上柜员要单位证明 → 转折
- 场景：江野 → 把批条推过去 → 柜员脸色变了 → 爽点（信息压制）
- 落点：出门时有人叫住他。钩子：王厂长在车里等着。
```

- `→ 爽点（类型）`：这一场给了读者情绪回报。类型写打脸 / 翻盘 / 揭秘 / 情感兑现 / 强强对话 / 信息压制 之一。
- `→ 钩子`：章末留翻页理由，**每章至少一个**。
- `→ 转折`：这一场把方向拐了个弯。
- 「爽点」是**这一场戏怎么演**的属性，不是一本账：**别单独建爽点表、别写到 outline 里当清单**。outline 的 `## 爽点节奏` 只写预算（`打脸×3`），实际有几处由章纲标记现算。
- 右栏章纲页顶部显示「爽点 N · 有爽点的章 X/Y · 最长断档 K 章 · 阈值 M」；`novel_check` 保留本章有没有爽点的信息，连续断档达到 M 才报 `no-payoff`，没有钩子仍报 `no-hook`。

**信息行（`- 信息：…`）—— 不是场景，别拿它凑数**

```markdown
- 信息：现在是 1998 年 9 月，他回到了十六岁
- 信息：三天后厂里会出事
```

- 判据：**能被拍出来的写 `- 场景：`**（有地点、有对手、结束时状态变了）；只在人物脑子里发生的（回忆、推断、前情交待）写 `- 信息：`。
- 回忆**不占场景位**：它挂在某个场景的「撞上什么」里（例：`撞上安全气囊弹开、玻璃碎进嘴里，他记得有人在车外敲了三下窗`）。整章都在前世时才当场景写。
- 一章最多 3 条信息；只有信息行、没有场景行 = 结构错误（`info-only`）；`info-missing` 仅表示字面近似匹配未命中，属于非阻塞线索，须读全文判断，不要求照抄或补写。
- 前世的**事实**（洪水、改制、谁死了）要落成 `settings/` 条目，不要只写在章纲或信息行里。

## 事件线（`events.md`）—— 跨章的主线 / 感情 / 反派

```markdown
## 主线：远离与反扑
- 目标：让她自己走到「求他」那一步
- 起点 → 终点：第 1 章 → 第 100 章

### 主线-1 真相落地（1–3）
- 因为：她亲眼看到离婚协议上的日期早于他说的「昨天」。
- 所以：她第一次主动找他核对时间线。
- 不可替代：换成别的理由，就没人会去翻那份协议。
```

- 二级标题 = 一条事件线（`## 主线：名字`、`## 感情：名字`、`## 反派：名字`），三级标题 = 这条线上的一个事件，`（起–止）` 是覆盖的章区间。
- 一个事件必须写清 `因为` / `所以` / `不可替代` —— **「不可替代」写不出来，这个事件就不该存在**（能换成别的理由推动，说明它不是主线）。
- 用 `novel_events({ line, content })` 整段替换一条线，不要手改文件；无参调用看全书事件线与推进情况。

**章纲里锚定事件（一章可以推好几条线）**

```markdown
## 0001 第一章

- 事件：主线-1、感情-1
- 场景：…
```

- 区间只是默认值：落在 `（起–止）` 里就算推进；写了 `- 事件：` 就是锚点，可提前、可推后、可跨线。
- 一章推 4 条以上就会散（`novel_check`/泳道会提醒）；一章一条主线 + 一条感情线是正常密度。
- 落在区间里却没锚，等于右栏泳道和装配包都以为这章不推线 → `novel_check` 报 `spine-unanchored`；锚了但超出区间报 `spine-conflict`。

## 伏笔表

```markdown
| 伏笔 | 埋设 | 回收 | 状态 |
| --- | --- | --- | --- |
| 投币箱里多出的那枚硬币 | 0001 | 0004 | open |
```

埋了就登记，用 `novel_threads({ thread, planted, payoff })`，不要手改表格。「回收」列写的是**计划**回收章，状态留空 = `open`，真收掉了才写 `done`——到期（计划回收章 ≤ 已写到的最新章）却没写的，右栏会标「到期」。

## 写作流程（每章都走一遍）

> 开书那一次还要多做一步：把主线拆成事件线写进 `events.md`（`novel_events`），并在每章章纲里用 `- 事件：` 锚好。没有事件线，写到第 30 章就会出现「主角在忙，但主线没动」。

**第 0 步：开书先立世界（只做一次，跳过它后面全是返工）**

在动笔写任何一章之前，先把世界观落成 `settings/` 里的条目，**至少 3 条、推荐 5–8 条**（地点 / 规矩 / 物品 / 术语 / 组织），每条一次 `novel_setting({ name, content })`，正文第一行必须是 `- 分类：…`。

- 世界规则、金手指的限制、社会规矩、行业黑话**必须落成设定条目**；
- 只写在 `outline.md` 里等于没写：outline 是给人看的散文，`settings/` 才是写正文时会自动装配进去的东西；
- 书名/题材/目标字数用 `novel_book`，那不算设定。

1. `novel_status` —— 现在写到哪、目标多少字、缺什么（设定 0 条时会当场提醒）
2. `novel_context({ chapter })` —— 拿「本章章纲 + 上一章结尾 + 出场人物卡 + 台账适用范围 + 未回收伏笔 + 相关设定」的装配包。`ready: true` 才表示全部 `[必选]` 文风已进入提示；旧章出现 `ledgerMissing` 时按提示查前文，不拿当前台账倒填。
3. 按装配包写正文（1000 字左右一章，别一句话带过一个场景，也别把三章的事塞进一章）
4. `novel_write({ chapter, content })` —— 落盘。目标字数仅供参考，超出不删减、不缩写、不提前收尾；先把当前场景的动作前提、空间过渡和因果后果写清。是否分章由情节自然节点决定，确需顺延尚未开始的后续场景时可传 `carryOver: true`，不能拆散当前动作链。
5. **交付前阅读全文审稿**：调用 `novel_deai_pack({ chapter })`，结合人物声口与文风锚点阅读全部正文，检查时间压力是否与描写、交涉相容，细节是否反复证明同一标签，旁白是否过度解释，句段和人物是否模板化。机械命中仅作线索，正常重复、长句、对比和修辞可保留，不强制短句、粗口或抢话。有问题才用 `novel_write({ chapter, mode: "patch", baseHash, patches: [{ start, end, content }] })` 一次保存多个修改；坐标均以同一版原文为准，不可重叠。原有单片段 `start/end/content` 写法仍可用。
6. 修改后重新调用 `novel_deai_pack` 审核最终版本，核对事实、意图、因果、数字与信息点未变。对包内每段填写 `{ index, reason }` 说明保留理由；带对话标签的段落另填 `dialogue.kind`（`speech` 实际对白 / `thought` 内心 / `quotation` 引用 / `uncertain` 无法确定）。实际对白必须填写 `speaker`、`listener`、`intent`、`pressure`、`assessment`，逐轮说明谁对谁说、想达到什么目的、现场压力和措辞是否当场听得懂；同段混有引用与实际对白时按实际对白审查，不把模糊狠话机械改成统一口语。按场景提交 `scenes`，用连续的 `startIndex/endIndex` 覆盖全部段落；本章有结构化章纲场景时，每场必须用 `sceneId` 声明该段对应的稳定场景 ID，不能按数组下标假定正文顺序等于章纲顺序，每个场景只能认领一个正文范围。每场记录 `layout`、`mechanism`、`timeline`、`actions`。每个关键动作记录段号 `index` 与 `actor/from/to/action/tools/prerequisites/result/timing/safety`，核对人物位置、通路、工具来源、状态变化前因、技术因果、耗时及危险禁令；同段多个关键动作分条列出。静态场景可用空动作数组，但须说明依据；不得脑补缺失步骤后登记完成。再填写 `checks` 的 `continuity`（连续性）、`timing`（时间压力）、`voice`（角色声口）、`narration`（设定投放、细节与解释）、`rhythm`（句段与冲突）、`facts`（事实与信息完整性），用 `novel_deai_review({ chapter, baseHash, checks, observations, timeBudgets, scenes, paragraphs })` 登记（启用文风时同时提交取包返回的 `styleHash`，不得沿用换卡前的取包结果）。每项 checks 提交 `{ verdict, detail, evidence, counterargument }`：verdict 取 supported/conflict/uncertain/not-applicable，至少一条 `{ source: "chapter", index, quote }` 正文逐字引文，确认矛盾至少两条不同引文；引用人物卡、设定、文风时注明 source 与 name，并先读取对应资料。说明最可能推翻结论的证据或缺失依据，不编造距离、耗时、器件结构或后文影响。发现矛盾和依据不足也应如实登记，工具保存为 blocked；记录完整不等于通过。旧阻塞项转为通过时另填对应 resolutions，说明修复依据或更正原因。再运行 `novel_check({ chapter })`；`deai-review-pending` 表示未完成当前版本复核，正文、引用资料或启用文风变化后旧复核失效，未复核或仍有阻塞项不能标记 `final`。`recorded` 只开放定稿资格，不自动把草稿晋级；作者明确要定稿且 `novel_check` 仍显示当前记录有效时，把当前完整正文原样作为 `content`，用 `novel_write({ chapter, content, status: "final" })` 显式定稿。`ai-tone` 或 `style-drift` 需结合语境审查，不能为了零命中强改正文；确有问题才局部修订，并重新复核。
   - 为什么不能拖到下一章：实测一份 80 章的书，句均字数从 17 一路掉到 10.1、对话段占比从 26% 涨到 64.5%——**漂移是累积的**，越晚纠越费事，而且后写的章会照着前面已经歪掉的稿子继续歪。
   - `novel_write` 写完也会自动跑一次节奏比对，返回里有警告就别装没看见。
   - 右栏章节列表里挂了「漂」红标的章，就是节奏已经偏离文风卡的章。
7. 有新人物就 `novel_card`，有新设定就 `novel_setting`，有新伏笔就 `novel_threads`，资产/境界/道具去向/伤势/时间变动就用 `novel_ledger` 更新 `ledger.md`

`ledger.md` 只保存人工维护的当前快照，更新同名项目会覆盖旧值。回改旧章时当前值不会装配，`ledgerMissing` 明确列出历史缺项但不阻断其他材料；须查目标章及其前文、人物历史或已有逐字证据，仍无依据时标为未知。不得为了回改旧章把旧值覆盖回当前台账。正常向前续写可读取当前状态；改写最新章时当前台账只作终态参考，不当作本章开场状态。

生成或改写前核对 `novel_context` 内的 `materialPreflight`，也可调用只读的 `novel_preflight({ chapter })`。章纲与文风的字面命中只是候选，逐项核对语义约束。正文是当前表述，设定是声明规则，人物卡是人物资料，文风是表达约束，章纲/大纲/事件线是计划，threads 是计划与可能过时的历史备忘。来源不同不自动证明谁错，不擅自覆盖资料；章纲内心原句默认不照抄，保留意图与情绪按文风表达。上下文预算不够时增加装配预算或继续读取资料，不缩写正文。

版本 6 必填 `observations`，无发现填 `[]`。每条填写 `aspect/classification/detail/evidence/counterargument`；classification 为 conflict（确定矛盾）、missing-basis（依据不足）、preference（表达偏好）。conflict 另填 `comparison: { entity, property, timeScope }`，至少两条不同证据，先排除同名异物、属性不同和时间变化。checks 的 conflict/uncertain 必须有对应观察；preference 单列为非阻塞建议。证据来源新增 threads/events，先读真实内容；备忘与正文不同先记缺失依据，不自动裁定谁错。追踪物件位置及状态，包含单据已填写/空白、佩戴/脱下、温度和交接。不同物件数量、“新”的模糊时间、人物自己的观察均不能直接当作矛盾。

登记时还须提交 `timeBudgets`：无窗口填 `[]`；有窗口列出同单位的明示时间、串并行阶段和任务。任务区分明示、估算、未知，未知不编数字；明示数值要有对应的逐字时间引文。估算与未知只限制记账结论，不自动证明正文有缺陷或动作可行；具体时间疑点另行说明对应区间与关系。不把一息换算成秒，也不为消除阻塞而往正文添加伪精确耗时。

按审稿包的 `sourceRequirements` 在对应维度引用人物卡、启用文风卡和相关设定；不能拿校准器件的说明代替角色声口或文风依据。检查工具回显的完整段落，不能用截取末句遮住反例。工具计算或来源覆盖产生的阻塞项不能用 supported 抹掉。

工具返回 recorded 只代表模型判断已登记，不得转述为“语义复核已通过”。时间记账成立不代表动作一定能完成，不得为解除提示向正文塞入计时句。近似统计位于 heuristicNotes，未命中反应词不能作为补写身体动作的理由。作者只要求检查时，保持正文不变，报告明确矛盾、依据不足和判断边界。

报告状态时照读工具回执的 status；存在阻塞项时为 blocked，不能把保存成功说成 recorded。机械及资料计数不是正文错误数。阶段已有明示时长时，不因阶段内缺少单步耗时就要求逐步标时；时间疑点须指出具体区间、动作关系或影响判断的缺失前提。记账相容仍不等于物理可行，修法也不能未经核实就声称不改变事实。

## 导入旧稿（已有的一整本 txt / 一堆 md）

不另设导入工具，按这个顺序用现有工具：

1. `novel_read({ source: 'D:\\路径\\旧稿.txt', limit: 4000 })` —— 自动认 UTF-8 / GBK / UTF-16，返回里带 `encoding`、`chars`、`nextOffset`。分批往下读，看清章节标题长什么样、有没有目录页。
2. **你自己判断章节边界**（插件不猜）：标题是哪一行、哪几行是目录、有没有缺章。
3. 逐章 `novel_write({ chapter, title, content, mode: 'replace' })` 落盘 —— 会自动留历史版本；章标题写进 `title`，不要写进文件名。
4. `novel_status` 核对：章数、总字数、有没有空章。
5. 需要再逆向提炼：`novel_outline`、`novel_card`、`novel_setting`、`novel_style({ clone: true, source })`。
   **长篇不要一口气读完**：每 8–10 章派一个 `subagent`，它只读原文、只返回「3 行摘要 + 出场人物 + 出现的专名/规矩」，由你汇总成大纲和卡片；子代理不许写文件。

## 红线

- **第一章开篇纪律**：前 300 字必须见冲突、异常或反常识奇观，禁止日常慢热或纯背景科普开局；即使主角表面吃亏，章末前也必须拿到实打实的筹码、信息优势或暗中收益，不写纯憋屈的第一章。
- 主线不许只写在 `outline.md` 的散文里：要落成 `events.md` 里**带因为 / 所以 / 不可替代**的事件。
- 一个事件跨好几章是正常的，别为了「一章一个事件」把它硬塞进一章。
- 爽点、钩子、信息行、事件锚点都写在章纲里，**不要另建资产文件**。

- **正文里不要出现 `## 关系` / `## 状态` / `## 0003 章纲` 这类结构标题**——那是卡片和章纲的格式，不是小说正文。
- 不要改动 `book.json` 的章节 id；新章节用 `novel_write` 或右栏「未写 +」建，不要手搓文件。
- 不确定的设定不要自己编；先问我，或者先在 `settings/` 里补一条再写。
- **世界规则不许只写在 `outline.md` 里**：金手指边界、社会规矩、地点规矩都要有 `settings/` 条目，否则写下一章时装配不到，前后必然打架。
- **`（待写）一句话梗概` 不是正文**：`novel_status` 会把这种章算成「占位」而不是「已写」。把梗概扩成真正的章节（1000 字上下，场景、动作、对话都要有），别拿梗概交差。
- 改别人已经定稿的段落之前先说一声。
- 写卡/写设定/写章纲之后，如果工具返回里出现「⚠ 格式提醒」，**要照着改一遍再往下写**：那说明刚才写的东西落盘了，但关系图/时间线读不到。

## 文风卡（`styles/<名字>.md`）

- 起卡：`novel_style({ clone: true, source })` 由当前会话模型提炼有证据的规则，生成待校准卡，保存参考原文并默认启用。只分析用 `novel_style({ source })` 或 `novel_style({ text })`。样本留档在 `styles/<名字>.sample.md`，右栏可查看开头。
- 校准：先用 `novel_style({ name })` 读全卡。对照多段锚点提炼视角权限、叙述距离、句法用词、对白声口、旁白分寸、描写和转场。每条候选写法附逐字引文与位置，证据不足时标待确认。原文很长时分段读取并核对跨段一致性。
- 试写：选同一新场景写约 500–800 字，可与基准版本并列。剧情、人物和设定以当前作品为准，勿移用样本的人名、事件或独特原句。只在对话中展示试写，经作者确认后才把长期偏好写回文风卡，局部意见留在本次。
- 写卡：结构见 `templates/style-card.md`。`novel_style({ name, content })` 保存，`novel_style({ name, active: true })` 启用。锚点保留连续原文，标题可加【通用】【对白】【动作】【心理】【过场】标签。统计观察用于对照，不设句长或对白配额。列表项开头的 `[必选]` 属于最低装配预算；预算不足会返回 `missingRequired` 和 `minimumBudget`，不得忽略后继续写。
- 复核：`## 禁忌` 一行一项，用「禁用词：」或「整句：」声明字面约束。`## 少用词` 仅提示，`## 语义禁忌` 由会话助手读正文和锚点核对。句长、标点提示需结合场景核实，再给出有原文依据的局部修订建议。

## 节奏与戏份：两个「承诺」的写法

- 大纲里写「三章一爽点」（或「每 3 章至少一次爽点」）：插件读这个数当断档阈值——状态条、章纲页、全书审计和 `novel_check` 共用同一结果，不是写死的 2。连续无标记章先记录 `hasPayoff/gap`，达到阈值才报 `no-payoff`；这是章纲计划统计，不自动判断正文质量。
- 打脸场的显式 `- 反应：` 只在当前结构化场景块内查，下一场不能抵扣本场；标签后没有实际内容不算已写反应。没标签只产生非阻塞字面线索，不要求补身体动作。正文已用对白、动作等自然体现时，在 `novel_deai_review.scenes[]` 的同一 `sceneId` 提交可选 `reaction` 及本场逐字证据，并带回审稿包 `beatsHash`。线索会保留并标注判断依据；整章 `recorded` 或 `rhythm: supported` 不能冒充本场确认。
- 人物卡里写 `- 戏份：每 8 章至少出场一次`：章纲 `- 出场：稳定ID` 只是计划，不能自动清零欠场；核实出场只认当前正文仍有效的**已确认 `登场` 记录（须带 `onStage: true`）**。画像、转述外貌、已知/关系等认知记录都只是呈现或转述。`- 提及` 和正文姓名/别名命中只作候选。查旧章先按书目顺序截断，未来章不抵扣当时欠场；人物页与 `novel_check` 显示相同截至章和依据。
- 两行都没写 = 用默认（每 2 章一次爽点、不检查出场）。**规矩要落成这两行，模型才会被约束**，写在正文散文里没人查。
## 小说心理与登场安排

心理材料按关键决定、误解、认知转变安排，不设每章数量、密度或逐句解释要求。主配角均可有心理，但能否直接呈现取决于场景叙述视角；非视角人物可标为“仅作者参考”，以外部行为间接表现。允许联想、短回忆、间接叙述，不强制写成台词。

人物块可写 `心理触发 / 心理内容 / 叙事作用 / 表达方式 / 展开程度 / 视角权限`。仅 `保留心声原句` 要求逐字保留。没有关键心理内容无需填写。

重要人物首次正式登场时考虑 `登场性质 / 观察者 / 描写重点 / 呈现时机 / 第一印象 / 已呈现与新增`；暗处、伪装等可填写 `不描写原因`。不按姓名出现次数自动判断初见，不要求全身扫描。身材、面容、衣着、声音等按人物和场景选取，后续以特征唤起和变化为主。

## 改写时的完整性约定

- `novel_context` 返回 `ready: false` 时，不得据此覆盖整章；先增大预算或使用 `rewriteStart` / `rewriteLimit` 获取片段。
- 默认先局部修订：`mode: "rewrite"` 获取范围后，用 `novel_write({mode:"patch",chapter,start,end,baseHash,content})` 保存；参数取自 `rewriteScope`，其余正文由插件保留。
- 保存后重新读取上下文，重新确定下一段范围，不直接复用旧索引或哈希。
- 全章改写必须拿到完整原文，保存时传 `baseHash`；先核对事实、动作、信息点全部保留，再检查文风。统计节奏偏差不自动意味着需要整章重写。

## 出场描写：第一次露面要交代

新人凭空说话最伤读者。章纲里给他一行：

``n- 场景：江野 → 教室门口 → 想直接走掉 → 撞上陆景明拦在门口 → 爽点（打脸）
- 出场：陆景明｜白衬衫、金丝眼镜，比同龄人高半个头，笑着递烟的样子像在替你着想
``

- 只在本章**第一次露面**时写；同章第二次出现不再写
- 一章最多 2–3 条，只在真有新人登场时
- 只写看得见的：衣着 / 体型 / 姿态 / 一个动作；身世性格交给人物卡
- 名字与描写用 ｜ 分隔，一句就够

## 时间线：生死用状态码，不写散文

人物卡里写：

```markdown
## 时间线
- @0001 已故｜死因：讨丹坠崖｜尸首：未寻回
- @0040 复活｜方式：被人在山里救起
```

- 状态码只有七个：`在世` `去世` `已故` `失踪` `假死` `复活` `远走`
- 行首必须是 `@章id 状态码`，后面用 `｜` 接字段（死因/地点/方式）
- `去世`＝书内死亡，`已故`＝开篇之前就死了——这两个界面标记不同，别混用
- **不要**写「死账」「死对头」「拼死」这类含「死」字的散文，也不要只写一个「死」字
- 不确定就写 `@0030 在世｜……`；不写状态码插件只能靠关键词猜，会误判
## 认知：这一章他此刻还不知道什么

穿越、失忆、新手、刚入行的角色，最容易写成"一开口就像本地老手"。章纲里给他一行：

```markdown
- 认知：第一次看见黑字，以为眼花；不知"系统"为何物
- 认知：认得坊市和三利号，那是原身的记忆
```

- 另起一行，写**边界**而不是身份（"他是穿越来的"是身份，"他不认识这屏字"才是边界）
- 一章 0–2 条，只在认知真的变了的时候写
- 装配包会单列「本章认知起点」，并提醒：不知道的别让角色装懂

## 场景人物与认知契约（2026-11-18）

本节替代前文关于人物动态关系、状态覆盖和逐行章纲的写作约定。新设计不提供旧数据迁移。

1. 人物卡顶部填写 `- ID：hero`、`- 定位：男主`、`- 重要程度：核心`。稳定 ID 全书唯一，不随姓名变化。全局卡记录稳定设定；作者侧秘密不等于人物已知。
2. 章纲每章仍为 `## 0001 标题`；每场为 `### 场景 scene-id：标题`，必填 `- 时序：10`、`- 出场：hero、heroine`；记录故事时间、地点、视角、冲突、具体事件 ID。时序是故事先后顺序的整数，不是章号；倒叙用较小值，建议预留间隔。
3. 每位出场者用 `#### 人物 hero` 块，写已知/未知/误信/怀疑及来源、目标、关系与情绪、表达意图、触发、计划变化。仅被提及者写入 `- 提及：ID`，不算知情或出场。
4. 写前调用 `novel_context({chapter:"0001",scene:"scene-id"})`；认知只继承更早时序、已确认且来源有效的历史。本场变化在触发后才能用于对白。未记录不代表明确未知。
5. 写后先用 `novel_deai_pack` 取得非空正文段号，并在 `novel_deai_review.scenes` 中按正文顺序连续分场；本章有结构化章纲时每场用 `sceneId` 声明对应的稳定场景 ID。逐场提取实际变化时调用 `novel_character_history({action:"propose",character:"hero",scene:"scene-id",kind:"已知",content:"认知内容",source:"亲历/转述等信息来源",evidenceIndex:7,evidence:"第 7 段中的正文逐字引文"})`。关系变化 kind 为 `关系`，另给 `target` 人物 ID；可给具体事件 `event`，纠正旧认知用 `supersedes` 记录 ID。
6. 候选只有在正文哈希、逐字段号、显式 sceneId、实际分场范围和章纲场景都一致时才返回 `binding.status: "bound"`；无法可靠归属时保持待核对。核对实际含义后，经作者确认或已授权流程调用 `confirm`（character+id）；不接受的候选用 `revoke`。历史落盘 `character-history/人物ID.md`。正文、分场或章纲场景变化会使旧记录待复核，必须重新提取；不把章纲计划自动确认。
7. 整场顺延用 `novel_move_scene({scene:"scene-id",chapter:"0002"})`，整块保留人物约束；不用旧的逐行 carryOver 拆分结构化场景。
8. 同场需要明确先后获得信息时，在人物块写清触发点；若需要在中途保存可继承状态，把该场拆成两个稳定场景 ID。当前确认记录的生效点为场景结束。

模板见 `templates/character-card.md` 和 `templates/scene-outline.md`（插件仓库资源）。


## 章纲 v2 操作补充

场景写 `- 叙述方式：限知/全知/客观`，`- 视角：人物ID`。人物块的心理与登场字段可选，见 `templates/scene-outline.md`。作者侧心理不自动获得正文展示权限，计划不等于已落实。

局部修改使用 `novel_stage_edit({chapter,scene,character,baseHash,fields})`，baseHash 取本次 novel_context 的 stage.baseHash；fields 为要修改的字段与单行值，空值删除字段。仅改章目标/收尾时省略 scene 和 character；仅改场景时省略 character。版本冲突后重新读取，不能盲目重试覆盖。

外貌或其他呈现写入正文后，可用人物历史 `kind: "呈现"` 连同 `evidenceIndex` 提交对应段的逐字引文，再按已授权的核对流程确认。读者已见的特征按章节阅读顺序继承，不等同于人物获知信息，也不证明人物本人登场；画像或他人口述外貌同样属于呈现。人物本人确实在场时用 `kind: "登场"` 并提交 `onStage: true`，只有它可以清零欠场。表现安排的语义核对清单不是机器证明未落实，不为清空清单而堆心理或外貌描写。
