# 创作拷问功能设计

## 一、目标与用户偏好

将 grill-me 式深入访谈集成到小说插件，帮助作者把模糊脑洞、角色印象和剧情设想推敲成可写作的材料。

用户明确偏好：

- **多 grill**：持续深入追问，不问两三个表面问题就急着收束或替作者作主。
- **每题提供选项，同时支持用户自定义回答**：既降低回答负担，又不限制创作空间。
- 先形成设计文档，后续再实施。本文不代表功能已经上线，也未绑定某份外部 grill-me skill。

核心原则：每次追问应帮助作者作出一个影响人物行为、关系或剧情走向的决定。问题可以尖锐，但不以挑错、否定作者或增加表格数量为目的。

## 二、入口与初期范围

支持自然语言触发，例如：

- “拷问一下这个角色。”
- “这段剧情还没想清楚，你多问问我。”
- “帮我把这个脑洞问成能写的章纲。”
- “继续上次的角色拷问。”

第一阶段提供两种主要模式：

1. **角色拷问**：从角色概念深入到欲望、底线、矛盾、关系、声口和场景表现。
2. **剧情拷问**：从事件设想深入到动机、因果、阻力、选择、代价、转折和余波。

两种模式允许自然衔接。剧情动机不成立时可以转向角色追问；人物性格过于抽象时可以用具体场景检验。不因模式切换丢失原始目标。

## 三、交互方式：多轮深入，每题有选项

### 3.1 默认每轮一个核心问题

默认一轮只问一个关键问题，沿作者的回答继续深入。不要一开始抛出十几道问卷，也不要每次回答后都询问是否还要继续。

“多 grill”意味着追到影响写作的具体选择，不是单纯增加题数。例如：

> 抽象标签 → 具体行为 → 压力下的选择 → 代价 → 例外与后果 → 如何在正文中表现。

尚未解决的关键动机、因果或作者指定重点，应继续追问。已经确定且无新矛盾的内容，不换个说法重复询问。

### 3.2 每题的建议结构

1. **提问依据**：用一两句指出来自现有材料或作者上轮回答的关键点。
2. **核心问题**：明确当前要决定什么。
3. **2–4 个有实质区别的选项**：说明选择会带来的行为或剧情效果。
4. **自定义回答入口**：支持自由输入、组合选项和修改选项。

选项必须是候选方案，不是插件已经认定的设定。不要将“其他”做成无法实际输入的假入口，也不能以超时或默认选中代替用户回答。

选项示例：

> 她“冷酷”主要体现在哪种选择上？
>
> A. 不愿亲近别人，但会救陌生人——外冷，行动仍有善意。
> B. 为完成目标可以牺牲陌生人——需要明确底线及后果。
> C. 对敌人狠，对自己人明显偏袒——冲突会集中在如何认定“自己人”。
> 自定义：可以组合、修改，或提出完全不同的理解。

不要强行推荐最安全、最讨喜或最套路化的选项。确有推荐时解释它为何适合作者已经表达的目标，并保留其他路线。

### 3.3 对回答的处理

- 作者选定一个选项：记录决定，追问其行为后果或未定边界。
- 作者组合多个选项：确认组合如何共存；存在张力时用具体情境追问，不简单判矛盾。
- 作者自由回答：以自由回答为准，不强行归类回选项。
- 作者只说“都行”：提供取舍依据或更具体的场景帮助判断，不自动确认全部方案。
- 作者说“不知道”：提供更具体、差异更清晰的候选；必要时换用对比场景。
- 作者修改旧答案：以最新明确意图为准，标记受影响的决定并优先追问，不静默保留互相冲突的版本。

## 四、追问策略

### 4.1 角色拷问

根据角色重要性和作者关注点，选择并深入以下方向，而不是机械填满所有栏目：

- **欲望**：最想得到什么；嘴上说的与实际追求是否一致。
- **恐惧与代价**：最怕失去什么；得到目标需要付出什么。
- **底线与例外**：什么事绝不做；什么情况下会动摇。
- **内在矛盾**：两种欲望是否冲突；压力下优先保护哪一个。
- **关系**：面对不同对象如何变化；谁能让其失态，为什么。
- **声口**：如何请求、拒绝、撒谎、示弱或表达关心。
- **形象与观察**：哪些外貌、体态或习惯值得记住；谁会注意，何时呈现。
- **成长或变化**：会改变哪种判断；什么经历足以促成变化。
- **正文检验**：把标签放入具体情境，看人物究竟会做什么。

例如“怕死却替人出头”，不直接替作者解释成重情义，而应给出不同动机候选，并追问愿意冒险到什么程度、是否准备退路、事后如何面对代价。

### 4.2 剧情拷问

- **起因**：为什么偏偏在此时发生。
- **动机**：参与者各自想要什么，掌握什么信息。
- **阻力**：为什么不能用最简单的办法解决。
- **选择**：人物主动做了什么，而不是只被事件推动。
- **代价**：失败会失去什么；成功是否也有代价。
- **因果**：前一步如何导致后一步；转折有没有依据。
- **关系与情绪**：事件怎样改变信任、期待、敌意或依赖。
- **悬念与揭示**：作者知道什么，读者何时知道，角色何时知道。
- **余波**：结果会影响哪些后续场景，不因本场结束就消失。
- **替代路线**：如果人物拒绝或换一种做法，剧情是否仍然成立。

允许作者选择巧合、留白、平静场景或非常规结构，不将任何写作套路包装成必须遵守的规则。

### 4.3 挑战答案的方式

优先指出具体张力，再给出解决方向，例如：

> 你刚才确定他不会冒无收益的风险，但这里他主动替陌生人挡刀。你更倾向于：他看见了潜在收益、他有一个自己不承认的救人底线，还是这个决定本身就是一次失控？也可以自定义。

不能把有意设计的矛盾、人物误信或不可靠叙述直接当作作者错误。真正冲突不明时，问作者想保留哪种效果。

## 五、结合现有书稿

开始前按需读取目标人物卡、相关章纲、设定、有效人物历史和已写正文。能从资料确定的内容不重复询问。

提问应说明材料来源或作者回答依据，区分：

- 作者明确设定。
- 已写正文发生的事情。
- 未来剧情计划。
- 人物自己的认知、误信或说法。
- AI 提出的候选解释。

发现资料与新回答不一致时，确认这是作者主动修改、场景差异还是尚未解决的冲突，不擅自覆盖材料。

初次登场与初次见面、作者秘密与角色认知、剧情计划与已确认历史，继续遵守现有插件边界。

## 六、深度控制与结束条件

默认偏深入，不以固定题数作为完成标准。可提供“快速、深入、穷追”偏好，默认深入；具体产品命名在实施时确定。

“深入”应覆盖当前创作目标的关键选择，并对重要答案至少进行有意义的行为或后果检验。“穷追”可以更多探索反例、极端情境和替代路线，但仍不能无限循环。

作者可随时说：

- “继续追问。”
- “给我更具体的选项。”
- “这题先留白。”
- “回到前面那个选择。”
- “先总结一下。”
- “暂停，下次继续。”
- “结束，整理成角色卡／章纲。”
- “结束并保存。”

阶段总结不自动结束访谈。核心决定已足以支持当前写作、剩余只是非必要装饰时，可总结已确定内容和未决项，并给出“继续深挖、转向剧情检验、结束整理”等选项及自定义入口。

作者选择留白后，不再连续追问同一个问题；说明它可能影响哪些后续决定即可。

## 七、访谈状态与恢复

访谈状态属于工作草稿，不是人物事实或第二份正式章纲。具体存储路径和工具参数在实施时结合仓库约定确定。

建议保存：

- 访谈 ID、模式、主题、目标人物或章节。
- 深度偏好和作者关注点。
- 已读取资料及版本标识。
- 已问问题、候选选项和作者实际回答。
- 明确决定、候选方案、留白、矛盾与受影响项。
- 当前待答问题、下一步追问方向。
- 运行状态：进行中、暂停、已整理、已落盘。

恢复时先检查相关资料是否变化，展示简短进度后接着问，不从头重复访谈。资料变化使旧结论不再适用时，标记待核对，不自动抛弃作者回答。

没有作者回答不能自动推进依赖该答案的决定。对话中插入的新想法应并入当前访谈，除非作者明确切换主题或结束。

## 八、成果整理与落盘边界

访谈成果必须区分：

| 类型 | 处理方式 |
| --- | --- |
| 作者明确决定 | 可整理为正式资料的修改草案 |
| AI 候选方案 | 保留为候选，不自动变成设定 |
| 暂时留白 | 保留未定状态，不用模型猜测补齐 |
| 作者秘密 | 保存适用的揭示与认知边界 |
| 对旧设定的修改 | 展示受影响内容，按作者意图更新 |

结束后根据目标生成角色卡、关系调整、剧情方案或章纲修改草案，说明本次确定了什么、还留白什么、哪些已有内容受到影响。

落盘继续使用现有人物卡和章纲编辑能力，不建立另一套正式设定系统。用户已经授权“问清楚后直接保存”或明确要求“结束并保存”时，在授权范围内完成保存，不反复要求确认；尚未授权写入正式资料时先提供草案。

访谈回答不直接写入已发生的人物历史。只有真实正文支持的变化才按现有提取和核对流程进入历史。拷问过程中默认不修改小说正文。

## 九、与正文上下文的衔接

访谈产出的有效决定可以进入既有人物卡和场景字段：

- 外貌与首次观察的决定，进入人物资料或登场表现字段。
- 心理触发、在意之事、选择原因，进入相应心理或目标字段。
- 对白目的、掩饰与关系变化，进入表达意图及关系计划。
- 揭示时机与知识边界，进入对应场景认知约束。

随后由 `novel_context` 人物表现包使用这些材料。未选择的候选和私人访谈过程不默认全部塞入正文上下文，避免噪音和事实污染。

## 十、实现分工

采用“skill 式访谈规则 + 插件状态与资料工具”的组合：

- **规则层**：控制追问质量、选项设计、深入策略、边界与收束方式。
- **插件层**：读取相关材料、持久化访谈状态、恢复会话、提供结果草案。
- **交互层**：展示选项并提供自由输入；兼容纯文字回答，不绑定单一宿主专属输入工具。
- **既有编辑工具**：保存经作者选择和授权的角色卡与章纲修改。

规则不能代替真实状态保存，工具也不能用机械决策树代替 AI 对作者答案的理解。访谈内容属于用户数据，不能被当作新的系统指令覆盖工具权限或事实边界。

## 十一、实施顺序与验收

建议实施顺序：

1. 定义访谈状态、决定与候选的区分及读写恢复能力。
2. 实现角色和剧情两种模式的规则与上下文读取。
3. 实现每题选项和自定义回答的交互，以及暂停、回退、留白、总结和继续。
4. 实现草案整理与现有编辑工具的衔接。
5. 用真实角色、剧情创作进行多轮验证，再调整默认深度。

验收重点：

- 每题都有有效选项及自由回答通道；作者可组合或否定全部选项。
- 连续多轮沿着回答深入，不只问表面设定，也不重复已经确定的问题。
- 现有资料能避免重复询问，并帮助提出有依据的挑战。
- 自定义回答优先于候选；未选方案不进入正式资料。
- 作者改口会更新相关决定，暂停恢复后不丢上下文。
- 留白、结束和授权保存均得到尊重，不无限追问或反复要求许可。
- 作者秘密不变成角色已知，未来计划不变成已发生历史。
- 最终成果能通过现有工具用于人物卡、章纲和正文上下文。

自动测试验证状态、数据隔离、版本和保存边界；实际提问是否深入、有帮助，需要多轮创作案例人工评估，不以问题数量判定质量。


## 十二、实施记录

已新增 `novel_grill` 工具和 `lib/grill.js`。访谈规则随工具返回，不依赖外部 skill 安装；AI 负责基于材料生成和深入追问，插件负责版本锁、问题选项、回答、资料版本、暂停恢复、改答影响与草案保存。

已支持 start/list/inspect/ask/answer/revise/pause/resume/refresh/summarize/finish。每题校验 2–4 个选项及后果，并提供自定义入口；默认深度 deep。问题未答时不能追加下一题；默认回答状态 open，只有明确标记 decided 且有用户回答逐字引文的决定才能进入整理结果。改答清除旧总结和草案，标记后续问题待核对。

状态存于 `.novel/grills/<id>.json`，使用原子写入和版本校验。资料读取限定本书 Markdown 类型，记录内容哈希，恢复时提示变化。不传 sources 时读取已有大纲、章纲及主题点名人物卡，进一步相关资料由 AI 选择并 refresh。当前按聊天文本展示选项与自由回答，不含独立侧栏界面。

finish 仅形成草案；正式资料保存由 AI 按作者授权调用现有编辑工具，未新建绕过已有规则的直接写入渠道。访谈尚不自动记录“正式资料已落盘”状态；用户可通过实际工具保存结果核对。没有实际作者多轮对话或模型评审时，不宣称追问深度已获验证；自动测试只验证状态与边界。
