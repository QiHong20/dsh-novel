# 章纲功能重构规划：人物、场景与认知

> 记录日期：2026-11-18。状态：核心闭环已实施，宿主视觉与真实生成验收待完成。
> 本轮已开始功能实现。按作者要求，不考虑旧数据迁移和旧格式兼容。

## 一、问题与目标

当前人物资料偏向全局设定，AI 在扩写章纲和正文时，容易把“作者知道的设定”当成“人物此刻知道的事情”。人物经历、信息来源、关系变化和知情时点不够明确，导致提前知道秘密、对话反应雷同、关系突然变化等问题。

本次重构采用“每章是一出舞台剧、每个场景有自己的演员与入场状态”的组织方式。

核心目标：人物卡回答“这个人是谁”；事件记录回答“发生过什么”；认知经历回答“这个人如何得知和理解”；章纲回答“这一场谁在场、知道什么、想做什么，以及离场时改变了什么”。

预期结果：扩写同一场对话时，亲历者、听闻者、不知情者和误解者能够表现出不同的措辞、试探、隐瞒与情绪，而且这些差异可追溯到具体经历。

## 二、现有基础与设计边界

静态查看当前代码后，确认已有以下基础，但不代表已经具备完整的场景认知模型：

- `index.js` 的 `parseCardRole` 已识别人物“定位”，包括主角、男主、女主、男二、女二、男配、女配、反派、龙套。
- `parseStates` 已支持带章节起点的状态记录，主要用于状态、生死、行踪等信息。
- `parseBeatCognition` 已读取章纲中的“认知”等文字条目，但未形成明确的逐角色、逐场景认知关系。
- 已有 `events.md` 事件线、`novel_beats` 章纲工具、`novel_context` 上下文装配及 `novel_check` 检查入口。
- `client.js` 已有人物页、章纲页和事件线展示，可围绕现有入口重构。

设计继续遵守项目定位：Markdown 是资料来源，不引入第二套正文存储，不增加运行时依赖，不自动生成整本小说。插件负责结构、引用、状态计算与确定性检查；会话 AI 负责语义提炼和写作，作者保留修订权。

不做旧数据迁移、旧格式转换或双格式兼容。正式实施前，将本专项中采纳的任务同步到 `docs/功能规划.md` 的总施工图，避免两份任务状态相互冲突。

## 三、数据分层

### 1. 全局人物卡：稳定设定

保留一人一张人物卡，集中记录相对稳定的内容：

| 维度 | 内容 |
|---|---|
| 人物标识 | 稳定 ID、姓名、别名；改名不改变引用身份 |
| 叙事定位 | 主角、男主、女主、男二、女二、重要配角、反派、龙套等，可按作品需要组合 |
| 重要程度 | 核心、重要、一般、临时，与叙事定位分开 |
| 基础设定 | 身份、背景、外貌锚点、能力与限制 |
| 性格声口 | 第一反应、底线、说话习惯、常见小动作 |
| 长期驱动 | 长期目标、欲望、恐惧、核心矛盾 |
| 作者侧秘密 | 真实身份、隐藏动机等，明确不自动等于人物已知 |

本章情绪、临场目标、当前信任程度不反复覆盖全局卡。人物成长造成的长期变化也应带生效锚点，不能用后期性格覆盖早期场景。

### 2. 事件记录：客观事实与来源

事件线继续描述跨章节的情节推进；角色经历引用其中的具体事件节点，不能仅引用宽泛的“主线”。

事件节点应能表达：稳定事件 ID、所属事件线、事实摘要、故事时间、地点、参与者，以及正文来源的章节与场景。规划中的事件与已由正文确认的事件必须分开。

必须区分：

- 实际参与事件的人。
- 在附近但没有看到关键过程的人。
- 后来通过其他渠道得知的人。

“参与过”不等于“知道全部真相”；“没有参与”也不等于“不知道”。

### 3. 角色认知经历：谁在何时得知什么

以角色为主体记录认知条目，而不是将整条客观事件直接复制给所有参与者。

| 字段 | 含义 |
|---|---|
| 主体 | 哪个人持有这项认知 |
| 内容 | 他知道、相信或怀疑的具体命题 |
| 认知类型 | 已知、误信、怀疑、明确未知 |
| 信息来源 | 亲历、目击、转述、信件、推理等，并引用来源人物或材料 |
| 生效位置 | 章节、场景及必要的场内触发点 |
| 故事时间 | 与章节阅读顺序分开表达 |
| 关联事件 | 引用具体事件节点，可为空但应说明原因 |
| 后续修正 | 被哪个新条目补充、推翻或替代，保留原来的认知历史 |
| 依据 | 正文位置、确认状态及对应正文版本指纹 |

不穷举人物不知道的全部事情，只对本场关键秘密和容易穿帮的信息记录明确未知。资料没有写到的信息标为“未记录”，不能自动断言人物知道或不知道。

角色的“误信”仍然能驱动行为，但不能因此修改客观事实。

### 4. 动态关系：有方向、有原因、有时点

关系记录以“甲如何看待乙”为基本单位，不假设双方对称。

例如：甲因共同逃亡而信任乙；乙却因甲隐瞒身份而开始戒备。关系变化应引用触发事件，并标明生效位置。

第一版用可读的文字描述表达亲近、信任、亏欠、敌意及其原因，不引入缺乏依据的好感度数值系统。

### 5. 场景角色状态：写作直接使用的入口

每章包含有序场景，每场明确关联角色。角色在场景中的状态包括：

- 入场认知：与本场有关的已知、未知、误信和怀疑。
- 当前目标：这场戏想得到什么。
- 当前关系判断：此刻怎么看待其他关键人物。
- 情绪及原因：为什么戒备、感激、愧疚或愤怒。
- 表达意图：哪些会说、哪些隐瞒、哪些想试探。
- 场内触发：听到、看到或经历什么后才发生变化。
- 计划离场变化：本场预计新增或修正的认知、关系与目标。

入场状态主要继承已确认的历史，不要求作者每章手工复制全部经历。章纲只补充本场相关约束和计划变化；发现它与历史冲突时应提示处理，不静默覆盖。

## 四、章纲结构与示例

章纲从“场景清单”扩展为“场景清单 + 出场角色 + 入场状态 + 触发与变化”。每场有稳定 ID，插入或调整顺序不应破坏引用。

以下是内容示意，具体 Markdown 语法在实施第一阶段确定：

```markdown
## 0008 客栈对质

### 场景 scene-inn-question：客栈对质
- 故事时间：救援事件次日晚
- 地点：客栈后院
- 视角：女主
- 出场：主角、女主、男二
- 冲突：女主想问清救援原因，男二试图逼主角交代身份。
- 关联事件：event-rescue

#### 女主
- 已知：主角曾冒险救自己；来源为亲历。
- 未知：救援与旧约有关。
- 目标：确认对方为何救自己。
- 关系与情绪：感激主角，但对他的隐瞒有疑虑。
- 表达意图：先感谢，再追问，不直接指控。

#### 男二
- 已知：两人曾一起失踪；来源为店主转述。
- 怀疑：主角接近女主另有所图。
- 目标：逼主角解释。
- 表达意图：用信物试探，不假装亲历救援。

#### 主角
- 已知：自己是在履行旧约。
- 目标：保护女主，暂不暴露约定人的身份。
- 表达意图：可以承认救人，但回避具体动机。

#### 触发与计划变化
- 触发：男二拿出信物，女主认出家族纹样。
- 女主：从不知关联，变为怀疑救援与家族有关。
- 认知边界：女主仍不知道旧约的具体内容。
```

人物在本章第二场才听到秘密，就不能在第一场表现为已知。必要时将场景拆成多个信息阶段，或为变化标明触发点；不要求为每一句对白建立独立状态。

“提到某人”“某人出场”“某人听到了这句话”是不同关系。人物名字出现在正文里不能直接证明他在场或获得信息。

## 五、存储与状态计算方案

建议继续使用工作区 Markdown 文件：

- `characters/*.md`：全局人物设定。
- `events.md`：事件线与具体事件节点。
- `beats.md`：逐章、逐场景的角色安排与计划变化。
- `character-history/*.md`：按人物保存已确认的认知、关系和状态变化；这是拟新增路径。
- `chapters/*.md`：实际正文，继续作为事实核对依据。

认知和关系变化保存为带来源的记录；“截至某场的当前状态”由这些记录计算。派生索引或缓存可重建，不成为另一份人工维护的真相源。

避免三个位置重复维护同一件事：事件节点记录事实，人物历史记录对该事实的认知，章纲只引用相关内容并记录计划。

章节顺序、故事时间与获得信息的顺序不能混为一谈。倒叙场景按人物在该故事时点的经历装配；读者已看过的未来信息不能注入早期人物认知。时间关系不明确时要求补充锚点，并标记待核对，不猜测完整时间线。

第一版优先支持明确先后关系和显式时间锚点，不承诺自动理解任意自然语言时间、平行时间线或复杂时间旅行。

## 六、写作流程与上下文装配

### 1. 扩写章纲

1. 读取本章目标、相关事件节点和候选人物。
2. 将本章拆为场景，明确时间、地点、视角与实际出场者。
3. 装配各角色在入场时已确认的相关认知和关系。
4. 设计本场目标、冲突、信息传递及计划离场变化。
5. 检查信息来源与触发顺序，保存章纲计划。

不能用本章计划结尾的认知反过来生成开场对白。

### 2. 扩写正文

`novel_context` 应支持按章节或场景装配，清楚区分以下区域：

- 本场目标、动作链和视角约束。
- 出场角色的稳定设定摘要。
- 各角色入场时的认知、关系、目标与表达意图。
- 场内计划触发与变化，明确标记尚未发生。
- 作者侧事实与秘密，明确禁止角色无来源地使用。
- 相关历史证据和可进一步读取的引用。

预算优先保证当前场景的关键认知边界、信息触发顺序、角色目标和必要正文。其他材料按相关性选择，不按人物全书地位盲目塞入完整卡片。

装配结果应列出已包含、已省略和缺失的资料。关键约束放不下时，转为按场景写作或补读，不能静默截断。

### 3. 正文完成后的确认

区分两套生命周期：章纲变化是“计划”；从正文提取的变化是“待确认 → 已确认”，来源改变后可变为“待复核”或被撤销。

正文保存后由会话 AI 提取实际发生的变化，并给出正文依据。经作者显式确认，或在作者已明确授权的写作流程中完成核对后，再写入人物历史。插件不因正文保存就自动将所有章纲计划标为已发生。

后续状态只继承已确认且来源有效的变化。缺少确认记录时显示状态缺口，补读正文或补做核对，不能假装资料完备。

## 七、界面规划

### 人物页

- 明确展示叙事定位和重要程度，支持筛选。
- 分开展示全局设定与“截至指定场景”的动态状态。
- 查看认知经历、关系变化、来源及首次得知位置。
- 区分作者侧秘密与角色当前已知，避免视觉上混淆。

### 章纲页

- 保留章节列表，展开后展示有序场景。
- 每场可关联已有角色，并区分实际出场与仅被提及。
- 点击角色查看入场状态、当前目标和计划离场变化。
- 标记继承自历史的内容与本场新增的安排，减少重复填写。
- 对缺少信息来源、计划与历史冲突、引用失效等情况提供定位入口。

### 写后核对

- 对照“章纲计划变化”和“正文实际变化”。
- 支持确认、修正、忽略候选条目；确认结果可追溯。
- 前文修改后展示受影响的后续条目和场景，不自动改写后续正文。

## 八、修改、顺延与一致性

- 修改正文：对应来源指纹改变后，将依赖该来源的确认记录标记为待复核；不能让过期记录继续作为可靠事实。
- 修改章纲：只影响计划，不反向改写已确认的人物历史。
- 场景顺延：连同角色关联、触发与计划变化一起顺延；重新计算入场状态，不能只移动场景文字。
- 场景重排或删除：保留稳定引用，报告无效引用与时序冲突。
- 认知被推翻：保留人物此前误信的阶段，新增修正记录，不覆盖旧历史。
- 人物改名：依靠稳定 ID 保持关联，显示名随人物卡更新。

插件可以确定性检查引用存在性、字段完整性、显式时序和来源有效性；“这句话是否泄露秘密”“情绪是否合理”属于语义核对，需要 AI 结合正文给出理由，不能用关键词命中冒充可靠判断。

## 十、验证场景

| 场景 | 预期行为 |
|---|---|
| 甲亲历救援，乙只听过传闻 | 两人的认知范围和信息来源不同 |
| 两人都在现场，但只有甲看到信物 | 不自动把信物信息赋给乙 |
| 女主在第二场得知秘密 | 第一场仍保持未知，第二场触发后才变化 |
| 男二误信主角背叛 | 对话可体现误信，客观事件不被改写 |
| 主角知道秘密但不愿解释 | 已知与表达意图区分，不能强制说出全部信息 |
| 甲信任乙，乙怀疑甲 | 关系按方向独立记录 |
| 章纲计划揭密，正文没有落实 | 下一场不能继承计划中的知情状态 |
| 正文发生章纲外的信息传递 | 核对后记录实际变化，不限于章纲预设条目 |
| 前文救援过程被改写 | 相关认知标记待复核，并提示后续影响 |
| 倒叙写回相识之前 | 不带入后来建立的关系和秘密 |
| 场景顺延至下一章 | 引用保持有效，入场状态重新计算 |
| 人物仅在对话中被提到 | 不判定为实际出场或知情 |
| 缺少某项认知记录 | 显示未记录，不自动等同于明确未知 |
| 上下文预算不足 | 明确缺口并按场景处理，不静默丢弃关键约束 |

实现时对解析、引用、状态继承、来源失效和预算行为编写必要测试；另用真实章纲与正文做人工或模型语义核对。结构测试通过不等于对白质量已经验证。

## 十一、首版范围控制

首版重点是场景关联角色、明确认知来源与时点、记录实际变化并供后续继承。重要角色详细维护，临时角色按本场需要补充，不要求所有人物填写完整表格。

暂不引入复杂心理数值、全自动事件抽取服务、任意时间旅行推演或全书自动连锁改写。后续扩展以实际写作中的连续性问题为依据。

数据契约采用 Markdown 字段和 `character-history/人物ID.md` 内的 JSON 代码块。场景 `时序` 为明确的故事顺序整数，记录在场景结束生效；同场触发仍由写作约束表达，必要时拆场。事件引用沿用 events.md 具体三级标题的节点 ID；事实依据来自正文引文，不能因事件规划存在就视为已经发生。

写后候选由会话 AI 使用工具提交，不额外启动模型服务。界面提供核对依据后确认、撤销；失效采用整章正文与整场章纲指纹，宁可提示复核也不静默继承。

已实现阶段一与阶段二的核心链路，阶段三已有基础面板与影响警告。已补充正文证据定位和按时序、出场角色保守列出的受影响场景。宿主视觉验收及真实生成效果尚未验证。
