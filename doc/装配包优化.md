# AI 装配包优化方案

## 1. 目标与结论

目前的创作流程是：生成装配包，再让 AI 使用装配包生成正文。完整包希望能够直接复制到网页聊天；普通包允许子代理按需补读伏笔等资料。同一份包可以交给不同模型生成候选正文，由作者比较和选择。

这个方向值得保留：把事实、章纲、人物认知与文风集中管理，有利于减少幻觉、事件错位，并比较不同模型的写作表现。但现有实现还不能保证完整包自包含，也不能保证所有未来信息均被隔离。

本文依据当前仓库代码审查整理，未使用真实书稿逐章验证；以下方案尚未实现。代码定位以函数或组件名为准，后续行号变化不影响定位。

## 2. 已确认的问题

### 2.1 完整模式不等于完整材料

位置：`index.js` 的 `novel_context`、`assembleNovelContext`，以及 `client.js` 的 `BeatContext`。

| 项目 | 当前行为 | 影响 |
| --- | --- | --- |
| 默认预算 | 网页完整模式显式传入 200000；后端只传 `full:true` 时仍默认续写 60000、改写 80000 | 两种调用方式行为不一致 |
| 台账 | 无论是否完整模式，适用的当前台账只取前 20 条 | 完整模式仍可能漏项 |
| 伏笔 | 普通模式最多 10 条，完整模式最多 500 条 | 放大数量不等于覆盖必要资料 |
| 设定 | 普通模式最多 4 条，完整模式最多 500 条，但仍先按名称命中选择 | 别称、隐含依赖、未点名的机制可能漏选 |
| 文风 | 仍有内部份额及可选条目取舍 | 完整模式不保证完整文风卡进入提示 |
| 最终预算 | 事件、设定、伏笔、上章结尾等仍为可选块 | 预算不足可省略，但仍可能 `ready:true` |
| 参数说明 | `full` 描述写着“给作者看……正文写作时不要用” | 与完整包直接生成正文的目标矛盾 |
| 界面文案 | 复制成功统一提示“已复制完整装配包” | 普通包或有省略项的包也可能被误认为完整 |

当前 `ready` 不能解释为“无需工具即可独立生成正文”。应区分必选块预算检查、资料充分性、章前预检状态和离线可用性。

### 2.2 伏笔时间筛选存在缺口

当前筛选近似为：

```js
item.open && (item.payoff === '' || item.payoff >= currentId)
```

主要问题：

1. 没有检查埋设章是否晚于目标章，未来伏笔可能提前进入。
2. 计划回收章早于目标章的未回收伏笔被排除，逾期遗漏反而消失。
3. 重写旧章时使用当前 `open` 状态；现在已经回收、当时尚未回收的伏笔可能丢失。
4. 普通模式取前 10 条，并非按本章关联度和到期程度排序。
5. 字符串章节 ID 比较不能普遍代表书目顺序。

应按目标位置重建伏笔状态，至少区分：此前已埋未收、本章计划埋设、本章计划回收、逾期待处理、未来计划。实际回收与计划回收必须分开；不能根据计划日期推定已经回收。

### 2.3 事件线筛选不是严格的未来隔离

当前规则为“章节区间命中，或本章／本场显式锚定”。普通未命中事件会被排除，但仍存在以下边界：

- 显式锚定可以绕过区间。它可能是作者调整，也可能是误挂，应提示冲突并核实意图。
- 区间使用章节 ID 字符串比较，章节重排或非标准编号时不可靠。
- 跨多章事件整段装入 `because/so`；如果字段包含最终结果，早期章节也能看到。
- 当前事件包不充分区分“本章允许推进到哪里”和“整条事件最终如何结束”。

建议按事件节点记录触发条件、前置事实、本章行动、允许结果及后续计划，不把跨章总结果直接当成本章结果。

### 2.4 未来信息还有其他入口

只过滤事件线不足以保证整个包没有未来信息：

- `outlineExcerpt` 匹配不到目标章时回退到大纲全文开头，可能包含未来概述。
- 人物卡全文进入包，作者秘密与未来变化可能混在其中；提示“作者侧”只能约束使用，不能形成数据隔离。
- `materialMemoSections` 会选择通用备忘、历史等小节，没有统一的目标时间切片。
- 设定正文也可能混合稳定规则、未来揭示和当前角色尚不知道的信息。

应分别管理故事事实发生时间、人物获知时间、读者已见顺序、作者计划和允许揭示范围。倒叙尤其不能只用一条时间轴处理。

## 3. 已有设计应保留

- `stage.js` 的 `sceneState` 会筛选已确认、来源有效、故事时间早于当前场景的认知记录。
- 场景提示区分计划与事实，不把同章前场计划自动当成已确认历史。
- 人物此前呈现信息与人物认知分开处理。
- 旧章或已写章内部片段不会直接装入当前台账值，避免拿未来终态倒填历史。
- 改写包携带原文和版本指纹，预算不足时不返回残缺原文供整章覆盖。

上述机制应继续使用，但历史值缺失仍然是缺项，不能因为没有装入错误值就宣称资料完整。

## 4. 建议的装配模式

### 4.1 工具辅助模式

用于主代理或具有读取工具的子代理：

- 先装入本章核心资料，明确列出缺项及可读取的来源。
- 补读仍须遵守目标章／场景边界，不允许通过全书搜索绕过隔离。
- 缺失关键事实时报告缺项，不自行编造。
- 如需多模型比较，先统一补读并冻结最终包，再分发。

### 4.2 独立生成模式（完整模式）

用于网页聊天和无工具写作子代理：

- 完整是“覆盖本次任务必要信息”，不是“把全书资料塞进去”。
- 本章必要事件、人物、设定依赖、伏笔及承接信息必须进入最终提示。
- 仍无法确定的关键事实必须明示；必要依据不足时不标记为可独立生成。
- 预算不足时返回缺项、所需预算或拆场建议，不静默省略必要材料。
- 不把调用插件工具、保存文件、登记审核等指令作为网页正文生成的必需步骤。
- 审核与保存协议留给主代理；写作包主要说明事实边界、文风和正文交付要求。

建议新增独立完整性结果，例如 `selfContained`、`missingMaterials`、`omittedMaterials`，保留 `ready` 的兼容语义并明确说明。不能仅靠改名就宣称语义完整；需要来源覆盖检查和明确的缺项规则。

## 5. 冻结装配包与多模型候选

推荐流程：

1. 主代理完成章前预检、资料补读与边界检查。
2. 生成最终装配包，记录目标章／场景、来源版本、装配规则版本及包哈希。
3. 把同一个包交给独立写作子代理或复制到网页聊天。
4. 子代理返回正文和缺失依据，不自行修改正文文件或更新台账。
5. 主代理用统一标准审查候选，作者选稿后保存并完成复核流程。

各候选应记录包哈希、实际模型、可获取的生成参数及生成时间。模型名称等运行信息放在候选元数据中，避免无必要地改变共同写作输入。

如果某个候选自行补读了额外资料，必须记录差异；需要严格比较时，应补齐共同包后重新生成。相同输入有助于公平比较，但不保证模型结果一致或自动消除幻觉。

## 6. 子代理提示与模型选择

### 6.1 当前状态

`BeatContext` 的“放入主对话”按钮只要求按包生成或改写正文，并在对话中展示，没有明确要求开启写作子代理。

`templates/AGENTS.md` 的常规写作流程也没有正文必须委派的要求；其中对子代理的明确要求主要涉及长篇原文分块分析等任务。

### 6.2 委派协议

建议在正文生成入口及写作规范中统一规定：

> 完成预检与装配后，新建写作子代理，将冻结装配包作为写作依据。子代理返回正文和缺失依据，不修改书稿文件。完整模式不得自行补读全书资料；关键依据不足时明确报告。主代理负责审核、展示和保存。

强提示只能提高遵循率。若需要保证实际委派，应由插件调用宿主的子代理接口，并记录执行结果。宿主不支持时明确显示能力限制，不能把主代理直接生成伪装为子代理执行。

### 6.3 模型选择功能

建议界面提供：

- 写作方式：子代理生成／复制到网页。
- 写作模型：读取宿主实际可用模型，支持默认继承。
- 候选数量：同包生成多个版本。
- 生成状态、取消操作、实际模型和包版本记录。

模型选择必须传入真实调用参数，不能仅在提示词中写“使用某模型”。若指定模型不可用，不应静默换成其他模型。

当前仓库尚未确认正文子代理模型选择链路。实施前需核实 DSH 宿主是否提供模型枚举、子代理创建、逐次模型指定、结果回传和取消接口。不能用当前 Codex 环境的能力推定 DSH 的能力。

## 7. 实施顺序

### 第一阶段：修正筛选与提示

1. 修复未来伏笔进入、逾期伏笔遗漏和旧章状态恢复问题；无法恢复的历史状态明确报告。
2. 统一章节顺序比较，以书目顺序为依据。
3. 统一网页与工具调用的完整模式预算，消除台账固定 20 条造成的静默漏项。
4. 修正“正文写作不要用完整模式”等冲突提示和复制成功文案。

### 第二阶段：建立独立生成保证

1. 区分必要材料和可选材料，输出覆盖清单及缺项。
2. 为设定、事件和伏笔建立显式依赖，名称匹配只作为补充发现方式。
3. 收紧大纲、备忘、人物卡和设定的未来信息入口。
4. 将作者计划、人物认知、读者已知和本章允许揭示信息分开。
5. 输出适合无工具环境的写作包，必要资料不全时禁止标记为独立完整包。

### 第三阶段：接入模型与候选管理

1. 核实并接入 DSH 子代理能力。
2. 增加模型选择与明确委派协议。
3. 保存冻结包和候选元数据，支持同包多模型比较。
4. 统一审核与选稿保存流程。

## 8. 验收场景

- 写第 5 章时，第 8 章计划埋设的伏笔不进入已发生事实；本章明确计划埋设的伏笔可以进入，但标为计划。
- 第 3 章计划回收、当前仍未回收的伏笔，在第 5 章显示为逾期待处理。
- 重写旧章时，根据实际埋设／回收依据重建当时状态；依据不足时明确缺失。
- 调换书目顺序或使用非标准 ID 后，历史与未来边界仍按书目正确判断。
- 本章锚定区间外事件时产生明确提示；跨章事件不自动暴露或执行后续终局。
- 未来信息出现在通用备忘、大纲开头、人物卡或设定中时，不被误当成本章可用事实。
- 倒叙中分别验证故事时间、角色获知时间与读者已见顺序。
- 完整模式遇到第 21 条必要台账、名称未命中的必要设定、预算不足时，不静默漏项后仍宣称完整。
- 网页和工具传入相同参数时，采用相同默认预算与完整性规则。
- 导出的独立包无需插件工具即可理解任务；必要依据不足时列出缺项。
- 子代理执行记录包含实际模型；指定模型不可用时明确失败，不静默替换。
- 同包多模型候选关联相同包哈希；未选候选不会覆盖正式正文。

实施时对筛选、预算、完整性和模型路由增加针对性回归测试，并以包含倒叙、跨章事件和历史改写的书稿样例验证整体效果。


## 9. 实施进度（第一批）

已实现：完整模式默认预算统一为 200000；取消完整模式台账 20 条及伏笔／相关设定 500 条限制；完整模式最终已选块全部参与必要预算检查。事件区间改按书目顺序比较。伏笔排除未来埋设、保留逾期项、识别状态列中的实际回收章，并报告埋设或回收位置未知的缺项。正文按钮及模板增加写作子代理委派协议。成功装配返回稳定提示哈希，网页接口透出缺项和省略清单。

完整性仍保守处理：`selfContained` 当前固定为 false；`selected-materials-complete` 只证明已选块未因总预算被省略，不认证依赖齐全或语义无冲突。设定依赖发现、文风内部取舍、未来信息旁路、历史台账恢复、实际模型选择与候选管理仍待后续实施。没有把尚未验证的宿主接口接成假模型选择器。

验证：全套 228 项测试通过 227 项；“超出八场只返回 warning，工具、原文与字段入口口径一致”失败，在隔离的 HEAD 基线中复现相同失败。新增回归覆盖完整模式事件预算、包哈希及非标准章节顺序下的伏笔边界；语法与 diff 空白检查通过。
